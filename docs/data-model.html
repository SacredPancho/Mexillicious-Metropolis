Metropolis Data Model

What a township is, what a cadet is, and exactly which field from the live session feed drives each thing you see on the plane.

Three entities

Everything on the plane resolves to one of these. Nothing else is persisted.

Persistent

Township

A project. Owns a hex cell, a theme, a skyline. Survives every session that touches it.

key: owner/repo

Ephemeral

Cadet

One live session, walking inside its township. Appears when a session becomes recent, leaves when it goes cold.

key: session id

Local only

Layout

Where each township sits. Yours, not the server's — never overwritten by a feed refresh.

Calls I made

Four places the data was genuinely ambiguous. These are now locked; changing one later means touching the renderer.

Locked

A session belongs to exactly one township

Sessions can carry several repos — this one carries two. Resolution order: first outcomes[] repo, else first sources[] repo, else the cwd basename from the local feed.

Why: outcomes is where commits land, which is the project being built. Letting one cadet stand in two townships doubles every count and makes the skyline lie.

Locked

Repo-less sessions get a Commons district

An unthemed hex adjacent to the cluster, holding every session with no repo attached. Cadets there behave normally and can be dragged out once a repo appears.

Why: this is not an edge case. In the live sample, 9 of 10 sessions had no repo field at all — only the cloud session carried one. Without a Commons, most of your work is invisible.

Locked

Skyline mass is spend, not commits

Sum usage.cost_usd across all sessions for a repo. Buildings are added at thresholds, never removed.

Why: it is already in the feed. Commit counts need a second API and a token, and they undercount design work that produced no diff.

Locked

Cadets expire, townships do not

A cadet exists if the session is RUNNING or REVIEW_READY, or its updated_at is inside 24 hours. Everything older is history, not population.

Why: you opened ten sessions in three days. Without expiry the districts fill with statues within a week.

Open questions

Two things I could not settle from the data alone. Both block backend work, neither blocks the renderer.

Unresolved

The two feeds use different session IDs

The account feed returns session_01H8krB7iQ…. The local claude agents --json returns a plain UUID for the same session. I have no evidence they can be joined.

Impact: until this is settled, the two feeds cannot be merged, so v1 uses the account feed alone. Local hooks stay a later enrichment, not a dependency.

Unverified

How your own app reads the feed

I reached this list through an MCP server available inside a Claude Code session. Whether a standalone app can call the same endpoint is unconfirmed.

Fallback that definitely works: the backend is itself a headless Claude Code or Agent SDK process with that MCP server attached. Worth checking the docs before any backend code is written.

What the feed will not give you

  • Push. There is no event stream — you poll. Pick an interval and accept the latency.
  • The question being asked. REVIEW_READY says a session wants you; it does not carry the prompt text. The bubble shows title until you open it.
  • A reply path. Nothing here writes back. Tapping Reply has to open the session, not answer it in place.
  • Complete history. The response paginates — has_more was true on the first page of ten.
